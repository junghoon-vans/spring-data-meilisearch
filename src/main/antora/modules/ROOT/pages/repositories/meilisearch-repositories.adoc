[[meilisearch.repositories.store-specific]]
= Meilisearch Repositories

`MeilisearchRepository<T, ID>` extends Spring Data `CrudRepository` and `PagingAndSortingRepository`.
The default implementation delegates to `MeilisearchOperations`.

This keeps repository usage aligned with familiar Spring Data patterns while still letting the module preserve Meilisearch-specific behavior underneath the repository facade.

[source,java]
----
import io.vanslog.spring.data.meilisearch.repository.MeilisearchRepository;

public interface MovieRepository extends MeilisearchRepository<Movie, String> {
}
----

This is the recommended repository style for the current module.
It exposes the standard Spring Data CRUD and pagination entry points without implying support for a wider derived-query feature set.

[[meilisearch.repositories.autocreation]]
== Automatic Settings Application

Repository bootstrap inspects the mapped entity type.
If the entity is annotated with `@Document(applySettings = true)`, Spring Data Meilisearch applies annotation-driven settings through `MeilisearchOperations.applySettings(...)` when the repository is created.

This behavior is store-specific.
It means repository creation can have side effects on the target index configuration, which is convenient for local development and controlled deployments but should be understood explicitly in environments where index settings are managed separately.

[[meilisearch.repositories.lookup-methods]]
== Built-in Repository Methods

The built-in repository methods do not all use the same underlying Meilisearch API:

* `findById(...)` and `existsById(...)` use direct document lookup; `findAllById(...)` uses native ID-list fetch.
* `findAll()` lists documents in one request; sorted `findAll(Sort)` counts first, then fetches once. A paged `findAll(Pageable)` uses search APIs, while an unpaged `Pageable` uses document listing.
* `count()` uses `SearchOperations.count(...)`.
* `save(...)`, `saveAll(...)`, and delete methods delegate to `MeilisearchOperations` document-oriented write operations.

`pagination.maxTotalHits` limits search-backed reads, not document-backed listing.
`displayedAttributes` can still restrict fields returned by document-list requests that omit `fields`, leaving mapped entities incomplete.
Document-backed reads require a key with `documents.get` permission.

[[meilisearch.repositories.lookup-methods.behavior-table]]
=== Method Behavior at a Glance

[cols="2,3",options="header"]
|===
| Repository method family
| Backing behavior

| `findById`, `existsById`
| Uses direct document lookup after converting the repository id through the configured converter.

| `findAllById`
| Uses native ID-list fetch, available from Meilisearch 1.14.

| `findAll`, `findAll(Sort)`
| Lists documents in one fetch; sorting counts first and uses the document API from Meilisearch 1.16.

| `findAll(Pageable)`
| A paged `Pageable` builds a search query and unwraps Meilisearch search hits back into entities; an unpaged `Pageable` lists all documents in one request and preserves its sort.

| `count`
| Delegates to the operations layer count support rather than maintaining a separate repository-side count strategy.

| `save`, `saveAll`, `delete*`
| Delegates to `MeilisearchOperations` write and delete operations.
|===

[[meilisearch.repositories.paging]]
== Paging and Totals

`findAll(Pageable)` selects its backing API based on whether the `Pageable` is paged.
A paged `Pageable` is backed by a `BasicQuery` plus search result metadata.
Its `Page` total is therefore derived from Meilisearch search totals, not from a separate count query.
If the index is configured with `@Pagination(maxTotalHits = ...)`, that limit can cap the returned search content even when the reported total is larger.

An unpaged `Pageable` (including `Pageable.unpaged(Sort)`) retrieves documents in one request and returns the complete content in the requested order.
Its `Page` total is based on the retrieved document count and is not capped by `maxTotalHits`.

The search-backed design for paged repository pagination explains why those results do not expose richer search response data such as facets or federation metadata.
When an application needs those store-specific result structures, prefer calling `MeilisearchOperations` directly from the service layer.
